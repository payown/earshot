# Earshot 1.1.0 CloudKit production schema review

Status: source candidate prepared; exported Development schema and Production
deployment remain pending

Candidate: 1.1.0 build 200
Container: `iCloud.media.payown.earshot`
Database: private

## Decision requested from Michael: conceptual boundary only

Approve the seven compact projection entities and their deliberately excluded
data as Earshot 1.1's intended production boundary. This is not approval of the
actual CloudKit server schema: that decision must wait until the Development
schema is exported and compared field by field. Neither approval authorizes
Production deployment or a TestFlight upload.

## Costs of making this shape permanent

- CloudKit Production schema changes are additive. A deployed record type or
  field cannot later be removed or renamed, so an accidental or obsolete field
  becomes permanent schema baggage.
- Avoiding relationships removes CloudKit reference ordering and required-
  relationship compatibility risks, but also removes server-enforced
  referential integrity and direct relationship queries. Earshot's
  reconciliation and tombstone code must maintain those guarantees itself.
- `CloudFolderProjection` stores podcast and episode membership as whole JSON
  values. Concurrent membership edits therefore conflict at the entire-folder
  value rather than merging member by member; one device's membership edit can
  supersede another concurrent edit.
- Queue records intentionally duplicate a bounded episode metadata shell. That
  makes a queue item independently materializable, but metadata may be stale
  and consumes additional private-database quota.
- Per-device contribution records and tombstones need durable retention and
  compaction rules. Their long-term growth has not yet been measured in
  Production.
- Future features that outgrow this model will need new additive fields or
  record types while the original production fields remain.

These are accepted design tradeoffs only after the conceptual boundary and the
exported Development schema receive separate explicit reviews.

## Approved entity boundary

| Entity | Purpose | Important fields |
| --- | --- | --- |
| `CloudPodcastProjection` | Followed podcast and shared podcast preferences | Canonical feed URL, descriptive feed metadata, shared queue/notification/playback/Inbox preferences, high-water date, modification/deletion metadata |
| `CloudEpisodeStateProjection` | Meaningful per-device playback state | Feed URL, episode GUID, position, explicit rewind time, played state, modification/deletion metadata |
| `CloudQueueItemProjection` | Per-device queue contribution | Feed URL, episode GUID, queue position, bounded optional episode shell metadata, modification/deletion metadata |
| `CloudSettingProjection` | Approved shared application settings | Setting key/value and modification/deletion metadata |
| `CloudBookmarkProjection` | Bookmark state | Bookmark ID, episode identity, position, note, creation/modification/deletion metadata |
| `CloudListeningSessionProjection` | Listening history contribution | Session ID, episode identity, duration, speed, date, modification/deletion metadata |
| `CloudFolderProjection` | Folder hierarchy and membership | Folder ID/name/order, optional parent ID, JSON natural-key podcast/episode membership, modification/deletion metadata |

Every entity stores a source-device identifier where conflict resolution needs
one. There are no SwiftData relationships, required references, or unique
attributes. All nonoptional attributes have defaults.

## Data deliberately excluded

- The complete local Podcast and Episode catalogs
- Episode descriptions except the bounded optional shell fields needed to
  materialize a queued episode on another device
- Download paths, audio files, transfer state, and queued-download preferences
- StoreKit products, transactions, entitlement cache, and tip records
- Migration snapshots, migration markers, restore journals, and recovery files
- Artwork and URL caches
- Device-local settings and local-only podcast/episode state
- Logs, crash reports, analytics, contacts, credentials, and account identifiers

Both V10 application configurations remain `cloudKitDatabase: .none`. Only the
separate `CloudProjection` configuration can use
`.private("iCloud.media.payown.earshot")` when the build-time gate is enabled.

## Evidence already present

- The original 232,921-episode full graph was rejected because it blocked parent
  records and created a 1.41 GB WAL during initial export.
- The replacement compact projection converged 662 subscriptions between the
  physical iPhone and Mac, with matching compact-store counts and SQLite
  integrity `ok`.
- Build 184 snapshots confirmed downloads and StoreKit entitlement state did not
  mirror.
- Builds 192–199 exercised two-device queue, folder, position, history, status,
  remote deletion, and live-player behavior in Development CloudKit.
- `CloudKitSchemaCompatibilityTests` now locks the seven-entity relationship-free
  boundary and the permanent separation of application/device-local stores.

## Evidence still required before deployment

1. Export the actual Development schema from CloudKit Console.
2. Compare every exported record type and field with this source inventory.
3. Confirm the Production change is additive and contains no obsolete full-graph
   record types selected for deployment.
4. Save the export and review result as durable release evidence.
5. Receive Michael's explicit record-shape approval.
6. Ask separately for authorization to deploy to Production.
