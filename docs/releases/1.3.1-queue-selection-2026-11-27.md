## Queue behavior

The former **Edit** button activated SwiftUI drag reordering only. It did not
select rows. Queue now has **Select episodes** and **Done**. In selection mode,
episode activation toggles a checkmark instead of opening details or playing.
The count-carrying bar offers Remove from Queue, Download, Mark as played and
Mark as unplayed. Selected removal does not delete downloaded audio, does not
change Played state, and commits non-playing removals together so Queue
consumers receive one invalidation. A selected currently playing item is
removed last through PlayerService so automatic advance skips every other
selected item. Played changes use the existing EpisodeRepository batch path and
honor Keep finished episodes in Queue. Search limits the action to visible
matches; execution revalidates Queue membership. Done cancels selection without
changing the Queue.

**Queue options > Reorder Queue** independently activates native drag handles.
It is unavailable during search so partial-list indices cannot corrupt saved
order. The existing grouped move actions and positions remain in place. The
native iOS drag action may still be offered while explicit reorder mode is on.

**Settings > Quick Actions > Queue** now owns the previously fixed **Pick up
for move** and **Open episode details** actions. Both can be moved into any
enabled position or moved to Available. Old saved configurations acquire them
at the end of the enabled list, matching the prior fixed rotor order; an
explicit Available setting remains disabled after relaunch. The first enabled
applicable action remains the VoiceOver default; an inapplicable first action
leaves ordinary details activation in place. Turning off the rotor's details
item does not remove ordinary touch details navigation. If VoiceOver is on and
another configured action owns row double-tap, a separately labeled Details
button beside that row opens the compact sheet or wide iPad pane. It is absent
when Details is enabled in the rotor, when ordinary details is already the row
fallback, and during selection or reorder mode. The native reorder route
remains available even when the configurable pick-up item is off.

## Heat investigation boundary

Michael reported a hot phone while refreshing and cleaning Queue. A source
comparison from public 1.3.0 (329), internal 1.3.1 (332/333), and 334-equivalent
main finds no 333→334 changes in FeedRefreshActor, QueueRepository,
DownloadManager, RootView badge observers, PlayerService, or phone Watch
connectivity. Queue actions added presentation work on realized rows but no
new recurring timer. Each preexisting Queue save notifies Inbox/badge,
download enrollment, player preload and Watch observers; repeated single-row
removal can therefore cause bounded activity during refresh. The new selected
removal deliberately publishes one Queue notification for its non-playing
batch. Source review does not establish a thermal cause or sustained loop.
Physical temperature and background networking require separate device
evidence; another beta app or system activity could also contribute. No change
to refresh cadence or download policy is justified yet. The disposable held
refresh fixture compares idle Queue remove/mark against two active-refresh
remove/mark trials and waits for refresh to settle; it checks durable Queue
state, not device power use. On the disposable iOS 27.2 simulator, the combined
remove/mark UI wall times were 8.25 seconds idle and 8.26/8.29 seconds during
refresh. Both overlap trials settled without restoring the removed rows. Those
numbers include UI automation overhead and do not measure CPU or temperature.
